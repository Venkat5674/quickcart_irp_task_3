📦 Part A: Objects, Prototypes & ES6 Classes

⏱️ 0:45 - 1:45 (1 min)
🖥️ What to show on screen: Open part-a-objects-classes/products.js and run: node part-a-objects-classes/products.js in the terminal.

"In Part A, we addressed inconsistent product instantiation.

In Task 1, I created the Product constructor and attached displayProduct() directly to Product.prototype. This is critical for memory optimization because prototype methods share a single function reference across all instances via the __proto__ chain, rather than duplicating the function in memory on every constructor call.

In Task 2, I migrated to modern ES6 classes, extending ProductClass into ElectronicProduct and ClothingProduct. I used super() in the derived constructors because subclasses in JavaScript cannot access this before super() runs—otherwise, a ReferenceError is thrown due to the Temporal Dead Zone.

Finally, in Task 3, I implemented modern ES6 syntax for the checkout flow: an arrow function for discount calculations, a template literal for order confirmation, object destructuring for customer details, the rest operator for dynamic pricing totals, and the spread operator to create immutable product copies without mutating the original object."

Key Answers Highlighted: Prototype memory sharing vs constructor closure; __proto__ vs prototype; super() initializing this; immutability via spread.

🛒 Part B: Higher-Order Functions, Map, Set & Object Methods

⏱️ 1:45 - 2:45 (1 min)
🖥️ What to show on screen: Open part-b-array-methods/shopping-cart.js and run: node part-b-array-methods/shopping-cart.js.

"Moving to Part B, we manage a customer's shopping cart using declarative functional programming.

In Task 1, I used map() to transform cart items into item totals, filter() to select products with unit price over ₹2,000, and reduce() to compute the total cart value of ₹70,100. Unlike forEach() which executes side effects and returns undefined, map() produces a new transformed array, and filter() is completely pure without mutating the original cart. I also combined filter and reduce to calculate the Electronics total of ₹62,000.

In Task 2, I built an inventory tracker using a JavaScript Map. Map is superior to plain objects here because it allows any key type, maintains strict insertion order, and provides an instant .size property. For customer emails, I used a Set to remove duplicates in O(N) linear time.

In Task 3, I compared Object.freeze() with Object.seal(). While seal() permits modifying existing writable properties like price, freeze() makes the object completely read-only, preventing any modification, addition, or deletion."

Key Answers Highlighted: map() vs forEach(); pure non-mutating filter(); Map vs plain Object; Object.freeze() vs Object.seal().

🔍 Part C: JSON Handling & Output-Based Debugging

⏱️ 2:45 - 3:45 (1 min)
🖥️ What to show on screen: Open part-c-json-debugging/json-handling.js and run: node part-c-json-debugging/json-handling.js.

"In Part C, we tackle real-world API data serialization and JSON edge cases.

In Task 1, I serialized an order containing undefined, null, and a function. During JSON.stringify(), the deliveryDate with value undefined and the calculateTax function are completely stripped. This happens because JSON is a language-agnostic data format that intentionally excludes runtime JavaScript concepts like undefined and closures. However, null is safely preserved as a first-class JSON primitive.

In Task 2, I verified all 6 output prediction challenges: In objects, undefined is omitted, but in arrays, it converts to null to preserve indices. NaN and Infinity coerce to null because JSON numbers only support finite values. Single-quoted keys throw a SyntaxError because JSON strictly demands double quotes. Circular references throw a TypeError to avoid infinite recursion. And Date objects automatically call .toJSON() to output an ISO 8601 string."

Key Answers Highlighted: Why undefined/functions drop in JSON; array preservation via null; NaN/Infinity handling; circular reference TypeError.

⚡ Part D: Asynchronous JavaScript & Promises

⏱️ 3:45 - 4:45 (1 min)
🖥️ What to show on screen: Open part-d-asynchronous/order-processing.js and run: node part-d-asynchronous/order-processing.js.

"Part D covers JavaScript's asynchronous execution architecture.

In Task 1, we analyze the Event Loop. Synchronous code on the Call Stack executes first: 'Order Started' and 'Order Completed'. Then the Event Loop drains the Microtask Queue—which is why the Promise resolves next with 'Payment Successful'—before finally picking the setTimeout callback from the Macrotask Queue for 'Payment Processing'.

In Tasks 2, 3, and 4, I demonstrated the evolution of asynchronous JavaScript: starting with nested sequential callbacks, highlighting why callback hell causes inverted control and fragile error handling; then refactoring to clean Promise chains with .then() and .catch(); and ultimately writing a production-grade async/await placeOrder() function with try/catch for both success and gateway timeout errors.

In Task 5, I executed all 4 Promise combinators: Promise.all fast-fails when the payment service rejects; Promise.allSettled inspects all three outcomes; Promise.race settles with the first response at 1000ms; and Promise.any waits for the first successful resolution."

Key Answers Highlighted: Microtask queue priority over macrotasks; callback hell pitfalls; Promise chaining; all vs allSettled vs race vs any.
